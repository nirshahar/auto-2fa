# Auto2FA — Product Plan

This is the product spec and implementation roadmap for Auto2FA, formalized for future sessions to work from. Nothing described here is implemented yet unless a phase is explicitly marked done — check the actual code before assuming a phase is complete.

## Product spec

**Android app (client):** a settings screen (Compose Multiplatform, Material3, modern look) with three required fields:
- the desktop server's IP (the port is a fixed constant, not user-configurable — see Architecture decisions)
- the desktop's RSA public key (pasted in as text) — for encrypting the OTP code
- the desktop's TLS certificate (pasted in as text) — for pinning the HTTPS connection, since there's no CA

When an SMS containing a 2FA code arrives, the app intercepts it automatically, extracts the code, encrypts it with the configured RSA public key, and sends it to the configured server over HTTPS. No user interaction is required for a successful push.

**Desktop app (server + client):** runs both a background HTTPS server and a minimal UI, in one process.
- On first run it generates an RSA keypair (for decrypting pushed codes) and persists it. The private key never leaves the machine.
- It also generates a self-signed TLS certificate/keypair (for HTTPS) and persists it, separately from the RSA keypair above.
- A settings screen shows the current public key and TLS certificate (for the user to copy into the Android app) — this is display-only, not editable.
- When the server receives a push, it decrypts the payload with the private key and shows a small popup with the plaintext code and a "Copy to clipboard" button.

## Architecture decisions

These are the concrete choices this plan commits to. Where the product spec didn't pin something down, a default is chosen and flagged in **Open questions** below rather than left ambiguous.

- **Crypto:** RSA-2048, OAEP padding with SHA-256 (not PKCS1v1.5). OTP codes are short (a handful of digits), well within OAEP's ~190-byte plaintext limit for a 2048-bit key, so no hybrid/AES envelope is needed.
- **Key material:**
  - Desktop generates the RSA keypair via `java.security.KeyPairGenerator` on first launch if none is persisted, stores it locally (private key PKCS8 DER, public key X.509 DER, both base64), and never transmits the private key. It generates a second, unrelated keypair for TLS (see the HTTPS decision below) the same way.
  - Both the RSA public key and the TLS certificate are exchanged manually: the user copies each base64 string shown in the desktop Settings screen and pastes it into the corresponding field on the Android Settings screen. (QR-code pairing is a nice-to-have, see Open questions — now a bit more attractive since there are two values to paste instead of one.)
  - Android crypto code only needs the public key and `Cipher`/`KeyFactory` to encrypt — no keypair generation on the phone, ever.
- **Where crypto code lives (done):** `java.security`/`javax.crypto` APIs are available on both the `android` and `jvm` targets of `shared` (both are JVM-flavored targets), but not in `commonMain` (which compiles against Kotlin-common metadata, not the JVM stdlib). `shared/build.gradle.kts` defines a custom intermediate source set, `jvmAndroidMain` (`dependsOn(commonMain)`, depended on by both `androidMain` and `jvmMain`), for exactly this code. `kotlin.mpp.applyDefaultHierarchyTemplate=false` is set in `gradle.properties` because Kotlin's default hierarchy template conflicts with a manually-wired `dependsOn` graph. `RsaCrypto.encrypt` (RSA/OAEP-SHA256) now lives in `shared/src/jvmAndroidMain/kotlin/org/example/auto2fa/RsaCrypto.kt`, using `kotlin.io.encoding.Base64` (common stdlib) instead of `android.util.Base64` so it works on both targets. When desktop-side decrypt/keygen is implemented (phase 1 below), it belongs in this same file/object, not a new one.
- **Settings persistence (done, not `expect`/`actual` as originally planned):** each side just has its own independent implementation, since the two "settings" concepts aren't actually the same shape (Android's describes a remote server to talk to; desktop's is its own key material) and there was nothing real to share. Android: `Settings` (`serverIp`, `publicKeyBase64`, `tlsCertificateBase64` — no port, see the port decision below) behind `SettingsRepository`, backed by DataStore Preferences (`androidApp/src/main/kotlin/org/example/auto2fa/Settings.kt`). Desktop: `DesktopKeyStore` (`desktopApp/src/main/kotlin/org/example/auto2fa/DesktopKeyStore.kt`), which loads-or-generates both the OTP RSA keypair (`~/.auto2fa/keypair.properties`) and the TLS keypair/cert (`~/.auto2fa/tls-keystore.p12`, a real `java.security.KeyStore` in PKCS12 form) on startup.
- **Wire protocol (finalized with the user, done):** `POST https://<serverIp>:8443/push` (see the port and HTTPS decisions below — both post-date when this bullet was first written as plain `http://<serverIp>:<serverPort>`). Body is a small JSON envelope, `{"code": "<base64 RSA-OAEP ciphertext>"}`, `Content-Type: application/json` — chosen over a raw base64 text body for room to add fields later (timestamp, device id) without a breaking change. The DTO itself, `OtpPushRequest`, lives in `shared/src/commonMain/kotlin/org/example/auto2fa/OtpPushRequest.kt` (plain `@Serializable` data class, no platform dependency) specifically so the Android client and the desktop server both deserialize/serialize against the same shape instead of two independently-maintained copies. Both `androidApp`'s `OtpPushClient.kt` and `shared`'s `Server.jvm.kt` use it now. The server responds `200 OK` on successful decrypt, `400 Bad Request` (and drops the payload, no popup) if decryption throws — see Roadmap phase 4.
- **Android networking:** a Ktor client using the `Android` engine (`ktor-client-android`), added to `androidApp`'s dependencies (not `shared` — this is Android-specific, unlike the server). Implemented in `androidApp/src/main/kotlin/org/example/auto2fa/OtpPushClient.kt`.
- **No retry on push failure (finalized with the user):** `SmsReceiver` fire-and-forgets the push with a short client timeout (5s) and logs+drops on failure. No `WorkManager` retry queue — `goAsync()`'s execution window is short anyway, and this was an explicit choice over building a persisted retry queue.
- **SMS → network handoff:** `BroadcastReceiver.onReceive` cannot block on network I/O. `SmsReceiver` must call `goAsync()` and do the extract/encrypt/POST work in a coroutine (or hand off to `WorkManager`), not inline on the main thread.
- **Desktop popup rendering:** the Ktor handler runs on Ktor's own thread pool, not the Compose UI thread. `onOtpReceived` should push the decrypted code into a UI-observable state holder (e.g. a `MutableSharedFlow<String>` or a `mutableStateListOf<String>` collected via `LaunchedEffect` in the Compose `application {}` block), which then opens a new small always-on-top `Window`/`DialogWindow` per code received — don't touch Compose state directly from the server thread.
- **Transport is HTTPS, pinned rather than CA-validated (finalized with the user, done):** there's no CA in this app's trust model, so instead of a real certificate chain, the desktop generates a self-signed TLS certificate (`shared/src/jvmMain/kotlin/org/example/auto2fa/TlsCertificate.kt`, via Bouncy Castle — the JDK has no clean public API for building an X.509 cert from scratch) and the phone pins that *exact* certificate (`androidApp/src/main/kotlin/org/example/auto2fa/TlsTrust.kt`, an `SSLContext` whose trust store contains only that one cert) instead of trusting the system CA store. Because we're already pinning the exact certificate, hostname verification is disabled on the Android client (`HostnameVerifier { _, _ -> true }`) — it would only guard against a *different*, validly-signed cert, which isn't a threat this trust model has anyway, and the phone connects by raw IP rather than a DNS name the cert would need to match. `launchServer` stopped being an `expect`/`actual` pair (the Android actual only ever threw `UnsupportedOperationException` — Android never called it) because its new signature needs `java.security.KeyStore`, which isn't visible from `commonMain`; it's now a plain function in `shared/src/jvmMain/kotlin/org/example/auto2fa/Server.jvm.kt` only.
- **Port is a fixed constant, not configurable (finalized with the user, done):** `AUTO2FA_SERVER_PORT` (`shared/src/commonMain/kotlin/org/example/auto2fa/ServerApi.kt`) is `8443` for both sides. There's no port field in Android's Settings UI or persisted `Settings` anymore — both apps just need to agree on one number, and making it configurable added a field for no real benefit.

## Roadmap

Each phase should be a self-contained, buildable step — verify `./gradlew :androidApp:compileDebugKotlin` and `./gradlew :desktopApp:compileKotlin` after each one.

1. ~~**Crypto & settings foundation**~~ — done, both sides. See the "Key material" and "Settings persistence" architecture decisions above for the current shape (both evolved since this phase was first written — `RsaCrypto` gained `decrypt`, `DesktopKeyStore` grew to also own the TLS keypair).
2. ~~**Desktop settings UI**~~ — done: `desktopApp/src/main/kotlin/org/example/auto2fa/SettingsScreen.kt` shows the base64 public key *and* the TLS certificate, each in its own card with its own copy button (the TLS certificate card was added later, during the HTTPS work — see phase 7). The old placeholder `shared/App.kt` (and its unused `compose-multiplatform.xml` drawable) were deleted since nothing calls them anymore.
3. ~~**Android settings UI**~~ — done: `SettingsScreen.kt`, wired into `MainActivity.kt`.
4. ~~**Server protocol update**~~ — done: `Server.jvm.kt`'s `/push` route parses `OtpPushRequest` (JSON) via Ktor's `ContentNegotiation`. **Note:** `launchServer`'s signature described when this phase was first written (`launchServer(port, decrypt, onOtpReceived)`) is now stale — see the "Transport is HTTPS" and "Port is a fixed constant" decisions below for the actual current signature (`launchServer(tlsKeyStore, tlsKeyStorePassword, decrypt, onOtpReceived)`, no `port` param). The server still has no idea what RSA is; it just calls `decrypt`, returns `400 Bad Request` and drops the payload (no popup) if `decrypt` throws, otherwise calls `onOtpReceived` with the plaintext code and responds `200 OK`. The old `OtpPush(sender, message)` data class is gone — there's no plaintext sender in the protocol, so it no longer made sense.
5. ~~**Android SMS → network wiring**~~ — done: `SmsReceiver.kt` extracts the OTP code from the SMS body via regex, encrypts it, and POSTs it via `OtpPushClient` inside a `goAsync()` + coroutine, fire-and-forget with no retry.
6. ~~**Desktop popup UI**~~ — done, after two real runtime bugs the user found by actually running it (this environment has no GUI, so it can't be verified visually — only by the user's own runs):
   - **Crash on every successful decrypt:** `OtpNotificationWindow` originally read `LocalClipboardManager.current` *before* calling the `Window(...)` composable it creates, but that composition local is only provided inside a `Window`'s own content, not the outer `application {}` scope — threw `IllegalStateException: CompositionLocal LocalClipboardManager not present` every time a code actually arrived. Fixed by moving the read inside `Window`'s content block.
   - **Buttons rendered as an unlabeled sliver:** the popup's original fixed `320x180` size didn't leave room for the title bar chrome + both text lines + the button row, so the row was clipped down to a barely-visible strip with no visible label text. Fixed properly (not by guessing a bigger constant) with `rememberWindowState(size = DpSize.Unspecified)`, which — confirmed by reading Compose Desktop's actual `Window.setSizeImpl` source — `pack()`s the window to exactly fit its measured content. This only works because the popup's content has no wrapping text and no `fillMaxWidth()`/`fillMaxSize()` anywhere in it; see the note below about why the *main* window couldn't use the same fix.
   - `desktopApp/main.kt` keeps a `mutableStateListOf<PendingOtp>` (each with a unique id from an `AtomicLong`, since `onOtpReceived` fires from Ktor's thread pool, not the Compose/AWT thread — Compose's snapshot state system is safe to mutate from a background thread, but a plain incrementing `var` id would not be), and renders one `OtpNotificationWindow` per pending code.
7. ~~**HTTPS for the `/push` call**~~ — done: see the "Transport is HTTPS" architecture decision above.
8. ~~**Main desktop window sizing**~~ — attempted the same `DpSize.Unspecified` wrap-content fix for the main settings window, but it doesn't work there and was reverted at the user's request back to a fixed `480x700` with an enforced `minimumSize` (`desktopApp/main.kt`). Two things make the main window a genuinely different case, not just an inconsistency to "clean up" later: (a) `SettingsScreen` uses `Scaffold`, whose layout unconditionally reports `layout(constraints.maxWidth, constraints.maxHeight)` regardless of content — confirmed by reading Material3's `ScaffoldLayout` source — so no content-side fix can make it wrap; (b) the screen shows long wrapping base64 text, which needs a fixed *width* to wrap against — a fully unspecified size would make the window balloon into one absurdly wide unwrapped line instead of a compact dialog. See CLAUDE.md's Architecture section for the full detail if this comes up again; the fix, if wanted, is `DpSize(fixedWidth, Dp.Unspecified)` plus dropping `Scaffold`, not blindly copying the popup's window state.
9. **Polish (not required for MVP)** — input validation on the IP field and connection-status feedback; encrypting the persisted RSA and TLS private keys at rest (both are currently stored in plaintext-equivalent form under `~/.auto2fa/`, protected only by OS file permissions); QR-code-based key/cert pairing instead of manual paste (now two values to paste instead of one, making this more attractive); retry behavior; migrating off the deprecated `LocalClipboardManager` to `LocalClipboard` (compiles fine today, just a deprecation warning in this Compose version); TLS certificate expiry/rotation (currently generated once with a 10-year validity and never refreshed).
10. ~~**Run the server in the background, independent of the settings window**~~ — done: `desktopApp/main.kt` already started `launchServer` before `application {}`, so the server was never actually tied to the window's lifecycle — the only thing killing it was the main `Window`'s `onCloseRequest = ::exitApplication`. Changed that to just hide the window (a local `isWindowVisible` state), and added a system tray icon (`Tray`, generated icon via `BufferedImage`/`Graphics2D` — no bundled resource) with "Open Settings" and "Quit" menu items; only "Quit" now calls `exitApplication()`. See CLAUDE.md's Architecture section for the detail. Not done as part of this: launch-at-login/true headless startup (the window still opens by default on launch) — flagged as a follow-up in Open questions below, not attempted here since the user only asked for closing the window to not kill the server.

**Status: the user has run both apps and exercised the real end-to-end flow at least twice**, which is how the two bugs in phase 6 above were found — this is no longer purely compile-verified, but it also hasn't been re-verified fresh since the most recent round of changes (the HTTPS/TLS work, the window-sizing fixes/revert, and the background-server/tray-icon work in phase 10). Before assuming everything above still works together, run both apps once more: generate a keypair on desktop, paste its public key + TLS certificate + desktop's LAN IP into the Android app, and send a real SMS through to confirm a code actually decrypts and pops up correctly over HTTPS — and confirm closing the settings window leaves the tray icon running and still able to receive a push.

## Open questions

Defaults were picked for these so the plan isn't blocked, but they're worth confirming before or during implementation:

- **Manual key/cert paste vs. QR pairing** — spec just says "a configured public encryption key," read as a manual paste for MVP; QR is listed as a polish item, not committed to. Now that there are two values to paste (public key + TLS certificate), this is a slightly stronger candidate for that polish item than before.
- **OTP extraction heuristic** — regex-based digit extraction won't handle every SMS format (alphanumeric codes, multiple number-like substrings in one message). Treated as an iterative heuristic, not a solved problem.
- **No auth beyond encryption on `/push`** — anything on the same network as the desktop can POST to it; only someone with the private key gets a meaningful decrypt, but there's no rate-limiting or replay protection. Flagged, not addressed, in this plan.
- **Launch at login / true headless start** — the tray icon (phase 10) makes the window optional after it's shown once, but the app still has to be started manually and the window still opens by default on every launch. Auto-starting at OS login and/or starting straight to tray (no window) are natural follow-ups, not yet requested or implemented.
