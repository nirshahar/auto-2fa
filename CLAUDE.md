# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state — read this first

This repo is a very early, unsettled prototype, not a finished app. All code lives under `Auto2FA/`, a single Kotlin Multiplatform (KMP) Gradle project — an earlier duplicate native-Android project (`android-app/`) and a Chrome-extension-based relay (`chrome-extension/`) have both been removed; the desktop app + server described below is their replacement.

**Read [PLAN.md](./PLAN.md) before starting product work.** It has the full product spec (settings UI, RSA key exchange, SMS interception, server protocol, popup UI), the architecture decisions made for it, and a phased roadmap. The "Not yet built" note below is superseded by that plan — treat PLAN.md as the source of truth for what's next.

**See [DISTRIBUTING.md](./DISTRIBUTING.md) for how the built artifacts get to a friend's phone/PC** — signed-but-unsigned-certificate release builds for both `androidApp` and `desktopApp`, and what each platform's install-time warning looks like. Note `androidApp/release.keystore` and `androidApp/keystore.properties` are real, gitignored local secrets (not committed) — see that doc before assuming `assembleRelease` is unsigned or regenerating them casually.

`Auto2FA/` has three Gradle modules:

- **`androidApp`** — the phone-side app (package `org.example.auto2fa`). Captures incoming SMS.
- **`desktopApp`** — the desktop-side app and server host (package `org.example.auto2fa`).
- **`shared`** — a KMP module (`android` + `jvm` targets) holding the shared Compose Multiplatform UI (`PermissionContent.kt`, in `commonMain` — Android-only in practice, see Architecture), cross-platform data/wire types (`OtpPushRequest.kt`, `ServerApi.kt` — which also holds the fixed `AUTO2FA_SERVER_PORT` constant — both in `commonMain`), the RSA crypto (`RsaCrypto.kt`, in a custom `jvmAndroidMain` source set — see Architecture), the desktop's self-signed TLS cert generation (`TlsCertificate.kt`, `jvmMain`-only), and the HTTPS server itself (`Server.jvm.kt`, also `jvmMain`-only — see Architecture for why this isn't `expect`/`actual` anymore).

## Commands

Run from inside `Auto2FA/` (this is the Gradle project root):

```bash
./gradlew :androidApp:assembleDebug   # build the Android debug APK
./gradlew :androidApp:compileDebugKotlin  # quick compile check, no full build
./gradlew :desktopApp:run             # run the desktop app (also starts the server)
./gradlew :desktopApp:hotRun --auto   # run the desktop app with hot reload
./gradlew :desktopApp:compileKotlin   # quick compile check for desktopApp + shared's jvm target
./gradlew test                        # run all tests
```

## Architecture

- **`shared`'s source-set layout is non-default — read this before adding code to `shared`.** Besides the usual `commonMain`/`androidMain`/`jvmMain`, there's a custom intermediate source set, `jvmAndroidMain` (wired via explicit `dependsOn()` in `shared/build.gradle.kts`, with `kotlin.mpp.applyDefaultHierarchyTemplate=false` set in `gradle.properties` because it conflicts with Kotlin's default hierarchy template). It exists because `java.security`/`javax.crypto` work identically on the `android` and `jvm` targets (both are JVM-flavored) but aren't visible from `commonMain` (which compiles against Kotlin-common metadata, not the JVM stdlib) — so code needing them but not tied to one specific platform belongs in `jvmAndroidMain`, not duplicated into both `androidMain` and `jvmMain`. `RsaCrypto.kt` there has `encrypt` (Android uses it), `decrypt`, and `generateKeyPair` (desktop uses both), all RSA/OAEP-SHA256, using `kotlin.io.encoding.Base64` (not `android.util.Base64`) so it compiles for both targets.
- **Wire-format types are shared, not duplicated per side:** `OtpPushRequest` (`shared/src/commonMain/kotlin/org/example/auto2fa/OtpPushRequest.kt`) is the `@Serializable` JSON body of `POST /push`. Both the Android client (`OtpPushClient.kt`) and the desktop server (`Server.jvm.kt`) deserialize/serialize against this one type.
- **Transport is HTTPS, pinned rather than CA-validated — there is no CA anywhere in this app.** The desktop generates a self-signed certificate (`TlsCertificate.generateSelfSigned`, via Bouncy Castle since the JDK has no clean public API for building an X.509 cert) and the phone pins that *exact* certificate (`androidApp/.../TlsTrust.kt`) rather than trusting a chain. `OtpPushClient` disables hostname verification on purpose (pinning already covers identity; the phone connects by raw IP, which wouldn't match a cert's CN/SAN anyway). The port is `AUTO2FA_SERVER_PORT` (`shared/.../ServerApi.kt`, `8443`) — a fixed constant on both sides, not a user setting.
- **Android app:** `SmsReceiver` (`androidApp/src/main/kotlin/org/example/auto2fa/SmsReceiver.kt`) extracts a candidate OTP code from incoming SMS via regex, encrypts it with `RsaCrypto.encrypt` using the public key from `SettingsRepository` (DataStore, `androidApp/.../Settings.kt` — Android-only; DataStore doesn't run on desktop JVM, and desktop's settings shape is different anyway, see below), and POSTs it via `OtpPushClient` (Ktor client, `androidApp/.../OtpPushClient.kt`, implements `shared`'s `ServerApi` interface, pinned per the TLS note above) — all inside `goAsync()` + a coroutine, fire-and-forget with a 5s timeout and no retry. `MainActivity` requests `RECEIVE_SMS` at runtime, then shows `SettingsScreen` (server IP, public-key and TLS-certificate paste fields — no port field) once granted.
- **Desktop app:** `desktopApp/src/main/kotlin/org/example/auto2fa/main.kt` loads/generates both keypairs via `DesktopKeyStore.loadOrCreate()` (RSA keypair in `~/.auto2fa/keypair.properties`, TLS keystore in `~/.auto2fa/tls-keystore.p12` — both desktop-only, not shared with Android, since desktop's "settings" is its own key material rather than a remote-server config), starts `launchServer` with a `decrypt` lambda closing over the RSA private key plus the TLS keystore/password, and opens the main `Window` showing `SettingsScreen` (base64 public key + TLS certificate, each with its own copy button, `desktopApp/.../SettingsScreen.kt`). Incoming decrypted codes are appended to a `mutableStateListOf<PendingOtp>` (each with an `AtomicLong`-generated id — `onOtpReceived` fires from Ktor's thread pool, not the Compose/AWT thread, so a plain incrementing counter isn't safe); `main.kt` renders one `OtpNotificationWindow` (`desktopApp/.../OtpNotificationWindow.kt`, an always-on-top window with "Copy to Clipboard"/"Dismiss") per pending item. This environment has no GUI/display, so nothing here can be verified visually from within a session — but the user *has* run both apps for real more than once (that's how the clipboard crash and the button-clipping bug below were found). Still, there's no live confirmation of the current HTTPS/TLS code specifically — see PLAN.md's roadmap status note before assuming it all still works together.
- **The app self-registers for Windows login on every launch of a packaged build.** `WindowsAutostart.ensureRegistered()` (`desktopApp/.../WindowsAutostart.kt`) is called first thing in `main()`. It writes a `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` value pointing at `"$exePath" --autostart` (`exePath` from `System.getProperty("jpackage.app-path")` — the running native launcher's own path, a property jpackage sets on its generated launchers, both the raw `createDistributable` app-image exe and an installed MSI's exe, but absent under `gradlew run`/the IDE, so it's a no-op in dev). This exists *instead of* baking autostart into the MSI installer itself: jpackage's Windows bundler has no supported option for a Run-key/shortcut/scheduled-task entry, and the Compose Gradle plugin's `--resource-dir` (`jpackageResources`) is hardwired to a plugin-internal scratch folder (`build/compose/tmp/resources`, verified by decompiling `AbstractJPackageTask`) with no exposed way to redirect it — so there's no supported hook to customize the generated WiX sources from `build.gradle.kts`. Re-running this on every launch is intentional (cheap, and self-heals the registry value if the install path changed). Known gap: no in-app toggle to opt back out — removing it means deleting the registry value yourself (or via Windows' Settings > Apps > Startup) and not relaunching the app, since the next launch re-adds it.
- **Autostart launches start hidden in the tray; every other launch still opens the window.** `main(args: Array<String>)` reads `WindowsAutostart.AUTOSTART_ARG` (`"--autostart"`, the literal arg `ensureRegistered()` appends to the Run-key command line) out of `args` and seeds the window-visibility `MutableState` with `!args.contains(AUTOSTART_ARG)` — so only the Windows-login-triggered launch defaults to hidden; the Start Menu shortcut, taskbar search, double-clicking the exe, and `gradlew run` (no args) all still open the Settings window as before. jpackage forwards a native launcher's own command-line arguments straight through to `MainKt.main(String[])`, which is what makes this possible without any IPC between the registry and the running process.
- **`SingleInstance` (`desktopApp/.../SingleInstance.kt`) exists because of the above, not on its own merits.** Once autostart can launch the app hidden, "open it" via the Start Menu/taskbar search would otherwise start a *second* process — which immediately fails to bind `AUTO2FA_SERVER_PORT` (already held by the first instance's server). `SingleInstance.tryAcquireOrNotifyExisting()` is called first thing in `main()`, before key generation or `launchServer`: it takes an exclusive `FileChannel.tryLock()` on `~/.auto2fa/instance.lock`; if that fails (another instance holds it), it connects-and-closes a loopback socket on a fixed port (`48432`, deliberately distinct from `AUTO2FA_SERVER_PORT` — this one only ever accepts a connection from the same machine, never a real OTP push) to signal the running instance, then returns `false` so `main()` exits immediately without touching anything else. The instance that *held* the lock spins up a tiny background `ServerSocket` on that same port and calls the `onShowRequested` callback (which just sets the window-visibility state to `true`, same as the tray's "Open Settings") on every incoming connection — verified end-to-end by launching the packaged exe twice: the second launch exited in ~0.3s with no second process left running.
- **The server runs independently of any window and survives the settings window being closed.** `launchServer(...)` is called in `main()` *before* `application {}` even starts, so it's never tied to a window's lifecycle. `main.kt`'s main `Window`'s `onCloseRequest` only flips a local `isWindowVisible` state to `false` (hiding the window) — it does **not** call `exitApplication()`. The process (and therefore the server) only exits via the tray icon's "Quit" menu item. A `Tray` (from `androidx.compose.ui.window.Tray`, requires no extra dependency beyond the existing `compose.desktop.currentOs`) is added in `main.kt` with a small generated-at-runtime icon (`trayIcon()`, drawn with `java.awt.Graphics2D` into a `BufferedImage` then wrapped via `toComposeImageBitmap()`/`BitmapPainter` — no bundled icon resource needed) and a menu with "Open Settings" (sets `isWindowVisible = true`) and "Quit" (`exitApplication`). **Known quirk, left as-is (not a bug to fix):** `Tray`'s `onAction` wires to `java.awt.TrayIcon`'s `ActionListener`, which on Windows only fires on a *double*-click of the icon once a popup menu is attached to it — a single left-click does nothing (right-click still opens the menu normally). A raw-AWT `MouseListener` workaround was tried and explicitly rejected by the user in favor of just living with the platform's default double-click-to-open behavior — don't reintroduce that workaround without being asked again. If a genuinely headless/no-UI mode is ever wanted (e.g. auto-launch at login with the window never shown), start with `isWindowVisible = false` instead of ripping out the window — the tray already makes the window fully optional after first launch.
- **Server (`shared/src/jvmMain/kotlin/org/example/auto2fa/Server.jvm.kt`):** `launchServer(tlsKeyStore, tlsKeyStorePassword, decrypt: (String) -> String, onOtpReceived: (String) -> Unit)` is a plain function, `jvmMain`-only — **not** `expect`/`actual` anymore. (It used to be, with an `androidMain` actual that only ever threw `UnsupportedOperationException` since Android never called it; once the signature needed `java.security.KeyStore`, which `commonMain` can't see, keeping the expect/actual ceremony for a function only one target ever calls stopped making sense.) It runs Ktor/Netty with an SSL connector built from `tlsKeyStore` (see the TLS note above), parses `OtpPushRequest` off `POST /push` via `ContentNegotiation`, calls `decrypt(request.code)`, responds `400 Bad Request` and drops the payload (no callback, no popup) if that throws, otherwise calls `onOtpReceived` and responds `200 OK`. The server itself knows nothing about RSA — that's entirely `decrypt`'s job, injected from `main.kt`.
- **Desktop window sizing is deliberately inconsistent between the two windows — don't "fix" this without rereading first.** `OtpNotificationWindow` uses `rememberWindowState(size = DpSize.Unspecified)`, which makes Compose Desktop size the window to exactly fit its content (confirmed by reading Compose Desktop's actual `Window.setSizeImpl`, which `pack()`s the underlying AWT window and reads back its content-driven preferred size). The main window (`main.kt`) does **not** use this — it's a fixed `480x700` (`MIN_WINDOW_SIZE`) with that also enforced as `window.minimumSize`. This was tried and deliberately reverted at the user's request; two real problems make `DpSize.Unspecified` a bad fit for the main window specifically: (1) its `SettingsScreen` uses `Scaffold`, whose `ScaffoldLayout` unconditionally ends with `layout(constraints.maxWidth, constraints.maxHeight)` — it always claims the full incoming space regardless of what its content measures to, so no modifier change inside it can make the window wrap; (2) `SettingsScreen` shows long, wrapping base64 text (public key, TLS cert) — with an unspecified *width* too, that text has nothing to wrap against and the window would balloon into one absurdly wide line instead of a compact dialog. (The correct fix for a screen like this, if wrap-content is wanted again later, is `DpSize(fixedWidth, Dp.Unspecified)` plus dropping `Scaffold` for a plain `Surface`/`Column` — exactly what `OtpNotificationWindow` already does — not blindly copying the popup's fully-unspecified state.)
- **Known rough edges:** `LocalClipboardManager` (used in both desktop UI files) is deprecated in favor of the newer suspend-based `LocalClipboard` in this Compose version — still compiles and works, just a warning. It must be read from *inside* a `Window`'s own content lambda, not from the `application {}` scope a `Window` is created from — reading it too early throws `IllegalStateException: CompositionLocal LocalClipboardManager not present` at runtime (this was a real crash the user hit and reported; fixed in `OtpNotificationWindow`, worth remembering if a new window/dialog is added). No input validation on desktop-side decrypt failures beyond dropping the request; no persisted-private-key encryption at rest for either keypair (both `~/.auto2fa/*` files are plaintext-equivalent, protected only by OS file permissions); the TLS cert has a 10-year validity and no rotation story. See PLAN.md's "Polish" phase and "Open questions" for the rest.
